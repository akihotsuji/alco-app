# セキュリティ監査

変更されたコード全体（diff）を対象に、以下のチェックリストで監査する。
**1件でもCriticalがあればマージ・リリース不可。** 修正してから再監査する。

## 監査手順

1. `git diff`（または対象ブランチとの差分）で変更ファイル一覧と内容を確認する
2. 変更に関係する既存コード（呼び出し元・ミドルウェア設定）も併せて確認する
3. 下記チェックリストを全項目実施し、結果を報告する

## チェックリスト

### 認可・認証【Critical】

- [ ] 新規・変更されたAPIエンドポイントは全て認証ミドルウェアを通っているか
- [ ] DBクエリ（select / update / delete）は全てセッション由来の `userId` でスコープされているか
- [ ] リクエストボディ・URLパラメータ由来の userId や所有者情報を信用している箇所がないか（IDOR）
- [ ] 更新・削除の条件が「ID＋userIdの一致」になっているか

### 入力検証【Critical】

- [ ] 外部入力（ボディ・クエリ・パスパラメータ）は全てZodで検証してから使用しているか
- [ ] 文字列結合による生SQLがないか
- [ ] 数値の範囲・文字列長・enum値がZodで制限されているか

### XSS・出力【Critical】

- [ ] `dangerouslySetInnerHTML` の使用がないか（あれば正当な理由と無害化の確認）
- [ ] ユーザー入力を `href` / URL に埋め込む場合、スキーム検証があるか

### シークレット【Critical】

- [ ] APIキー・パスワード・トークンがコード・設定ファイル・テストコードにハードコードされていないか
- [ ] `.dev.vars` 等のシークレットファイルがコミットに含まれていないか
- [ ] ログ出力にトークン・パスワード・個人情報が含まれていないか

### ファイルアップロード【High】

- [ ] サーバー側でContent-Typeとサイズ上限を検証しているか
- [ ] 保存キーがサーバー生成で、ユーザー入力のファイル名を使っていないか
- [ ] 配信経路に認可チェックがあるか

### エラー・情報漏えい【High】

- [ ] エラーレスポンスにスタックトレース・内部情報が含まれないか
- [ ] 権限のないリソースへのアクセスが404を返すか（403で存在を漏らしていないか）

### テスト【High】

- [ ] 「未認証は401」「他ユーザーのデータにアクセスできない」テストが変更対象のAPIに存在するか

### 依存関係【Medium】

- [ ] 新規依存パッケージの必要性は妥当か。`pnpm audit` に新たな警告がないか

## 報告フォーマット

```markdown
## セキュリティ監査結果

対象: <ブランチ/PR/diffの範囲>
判定: 合格 / 要修正

### 指摘事項
- 🔴 Critical: <ファイル:行> <問題と修正方法>
- 🟠 High: ...
- 🟡 Medium: ...

### 確認済み項目
（問題なしと確認したチェック観点を簡潔に列挙）
```

指摘ゼロの場合も「確認済み項目」を必ず記載し、何を監査したかを明示する。
