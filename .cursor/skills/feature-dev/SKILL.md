# 機能開発ワークフロー

alco-appで機能を実装・変更するときは、必ずこの手順に従う。

## 進行チェックリスト

```
- [ ] Step 1: 仕様の確認・作成
- [ ] Step 2: ブランチ作成
- [ ] Step 3: 実装（shared → server → client の順）
- [ ] Step 4: テスト作成・実行
- [ ] Step 5: ドキュメント同期
- [ ] Step 6: セキュリティ監査
- [ ] Step 7: セルフレビューとPR作成
```

## Step 1: 仕様の確認・作成

1. `spec/03-roadmap.md` で現在のフェーズと対象タスクを確認する
2. `spec/features/` に対象機能の仕様があるか確認する
   - **ある** → 仕様と実装内容に齟齬がないか確認してから進む
   - **ない** → 仕様ドキュメント（画面項目・バリデーション・API・エッジケース）を作成し、オーナーの承認を得てから実装に入る
3. 画面を含むタスクなら `spec/screen-designs/` の該当ファイルを開き、**要素表・状態・遷移・モック・受け入れチェック**を読む。実装はこのとおりに作る
   - 設計と違う作り方が必要なら、コードを書く前に設計ファイル（必要なら `spec/wireframes/mocks/`）を直し、PR 本文に「画面設計の変更点」を書く
   - キャラクターを出す画面は `spec/character.md` の配置表も確認する

## Step 2: ブランチ作成

`main` では作業しない。**切る直前に必ず `git fetch origin main` し、リモート先端から切る。** ローカル `main` や未フェッチの `origin/main` から切らない。

```bash
git fetch origin main
git checkout -b feature/<内容> origin/main
```

`fix/<内容>` も同じ。`git status` の "up to date with origin/main" はローカル記憶との比較であり、リモート最新を保証しない。

## Step 3: 実装

依存の少ない順に実装する:

1. `src/shared/` — Zodスキーマ・型・定数（クライアント/サーバー共通の契約を先に固める）
2. `src/db/` — スキーマ変更がある場合はDrizzleマイグレーションを作成
3. `src/server/` — Honoルート・サービス。認証ミドルウェアとuserIdスコープを必ず入れる
4. `src/client/` — 画面・コンポーネント。モバイル幅を基準に、`spec/screen-designs/` の要素表の順に実装する

## Step 4: テスト

- 計算・変換ロジック: 単体テスト（境界値を含む）
- API: 正常系＋「未認証は401」「他ユーザーのデータにアクセスできない」の認可ケース
- 実行して全てパスすることを確認: lint / typecheck / test

## Step 5: ドキュメント同期

実装中に仕様と差分が出た場合は `spec/features/` の該当ドキュメントを更新する。
ロードマップのタスクが完了したら `spec/03-roadmap.md` のチェックボックスを更新する。

## Step 6: セキュリティ監査

`security-audit` スキルに従い、変更差分に対するセキュリティ監査を実施する。
Critical / High の指摘がある場合は修正して再監査し、ゼロになるまでPRを作成しない。

## Step 7: セルフレビューとPR

1. diff全体を見直す（デバッグコード・不要コメント・console.logの除去）
2. 日本語でPRを作成する。形式は `.cursor/rules/development-workflow.mdc` に従う
3. PR本文に「仕様ドキュメントへのリンク」「テスト内容」「動作確認方法」「セキュリティ監査結果」を含める
4. 画面を含む PR は、`spec/screen-designs/` 該当ファイルの **受け入れチェックをそのまま貼り**、全項目にチェックを付ける。付かない項目があるならマージしない
