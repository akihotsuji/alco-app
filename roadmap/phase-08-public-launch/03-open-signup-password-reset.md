# 8-03 公開登録の確認・パスワードリセット

| 項目 | 内容 |
|---|---|
| フェーズ | Phase 8 一般公開準備 |
| ステータス | **未着手** |
| 要件 | v1.x パスワードリセット。招待制は 2026-08-13 に不採用で FIX |
| ソース | Phase 8「公開時の新規登録フロー確認、パスワードリセットメール」 |

## 1. 概要

一般公開に耐える新規登録と、パスワードをメールでリセットできる状態にする。メール送信基盤を初めて入れる。

**招待制は採用していない**ため、フラグ解除作業は無い。MVP 時点でメール＋パスワード登録は動いている前提。

## 2. 前提条件

- Phase 2-02 でオープンサインアップ済み
- 8-01 / 8-02 を公開登録の前に済ませるのが安全
- 送信プロバイダ（Resend 等）**要確認**。Workers からの送信制約

## 3. スコープ

**対象**

- 公開 URL での新規登録が仕様どおり動くことの確認
- パスワードリセット（Better Auth 標準。自前トークン禁止）
- メール送信の設定（secret は wrangler secret）
- メール文面（リセットリンク。ログにリンクを出さない）

**対象外**

- 招待フラグ/コードの削除（存在しない）
- マジックリンクログイン必須化（任意）
- メーリングリスト

## 4. 成果物

- Auth のメール設定
- リセット UI
- テスト（トークンを git に置かない。メールはモック）
- プロバイダ追加理由

## 5. 細分化タスク

1. 招待関連コードが無いことを検索で確認する
2. メールプロバイダ選定とコスト
3. Better Auth の email 設定
4. リセットフロー UI
5. レート制限（8-05 と同時が望ましい）
6. 監査

## 6. 手順

本タスクは **オープン登録の確認 + リセットメール**。招待解除はしない。

```powershell
git checkout -b feature/password-reset-email
```

送信 API キーは `.dev.vars` / wrangler secret。テストではコンソール出力バックエンド（公式の dev 用）を使い、実メールを CI から撃たない。

## 7. 仕様詳細

- リセットリンクの有効期限は Better Auth 既定を確認して spec に書く
- 未登録メールへのリセット要求も同じレスポンス（ユーザー列挙防止）
- FROM アドレスと SPF/DKIM。Workers.dev ドメインからの送信は届きにくい → 独自ドメイン（7-06）が事実上必要になりうる。**要確認**

## 8. 受け入れ条件

- [ ] 招待コードなしで登録できる
- [ ] リセットメールが dev で届くか、公式テスト手段で検証
- [ ] 独自トークン実装がない
- [ ] 列挙耐性
- [ ] 秘密が git に無い
- [ ] DoD / 監査

## 9. セキュリティ観点

- リセットトークンを URL の Referrer に漏らさない
- 送信 API キーの権限最小
- ログイン試行制限とリセット試行制限
- URL を公開した瞬間に登録口になる。8-05 未実装ならボット登録
