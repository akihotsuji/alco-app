# 8-06 無料枠の使用量監視と課金プラン検討

| 項目 | 内容 |
|---|---|
| フェーズ | Phase 8 一般公開準備 |
| ステータス | **未着手** |
| 要件 | コスト無料枠内が基本。超過時の方針 |
| ソース | Phase 8「無料枠の使用量監視と、超過時の課金プラン検討」 |

## 1. 概要

Workers / D1 / R2 / GitHub Actions の使用量を定期的に見て、公開後に突然課金されないようにする。実装というより運用と閾値の文書。必要ならダッシュボード通知。

## 2. 前提条件

- 本番が動いている
- [spec/02-tech-stack.md](../../spec/02-tech-stack.md) の無料枠表

## 3. スコープ

**対象**

- 監視項目と閾値（例: 80%）
- 確認手順（週次）を operations に追加
- 超過時の選択肢（新規登録停止、画像上限、Workers Paid 検討）
- Cloudflare の billing alert（設定はオーナー）

**対象外**

- 収益化
- 自動スケールの複雑な最適化

## 4. 成果物

- `spec/operations.md` への節追加、または `spec/capacity.md`
- （任意）シンプルな管理用使用量メモ。ユーザー向け画面は不要
- 課金に進む場合の判断基準（オーナー）

## 5. 細分化タスク

1. 現行無料枠を公式で再確認（数字は変わる）
2. 表を tech-stack と同期
3. アラート設定（オーナー）
4. 超過時プレイブック（新規登録の一時停止フラグ等。招待制は使わない）
5. R2 の写真枚数とリサイズが効いているかサンプル確認

## 6. 手順

ダッシュボード: Workers 分析、D1 メトリクス、R2 ストレージ。

GitHub: Actions 分。

文書に「確認日と公式 URL」を書き、数字のコピーが古くなったら更新する。

コードが必要なら `GET /api/health` に使用量を出さない（情報漏洩）。

## 7. 仕様詳細

tech-stack の目安（再確認前提）:

| サービス | 無料枠の記憶 | 個人公開で見ること |
|---|---|---|
| Workers | 10万 req/日 | ボット |
| D1 | 5GB・読取 | 全件スキャン API |
| R2 | 10GB | 未リサイズ画像 |
| Actions | 分 | E2E の頻度 |

超過時オプション（要確認）:

1. 新規登録クローズ
2. 写真上限を下げる
3. Paid プランへ（予算上限をアカウントに設定）

## 8. 受け入れ条件

- [ ] 監視項目と手順がある
- [ ] 超過時の方針がオーナー承認
- [ ] 使用量を公開 API に出していない
- [ ] tech-stack の数字が確認日付き

## 9. セキュリティ観点

- アカウントの課金情報を spec に書かない
- 分析ダッシュボードの権限を共有しすぎない
