# 5.5-04 Issue修正ループ

| 項目 | 内容 |
|---|---|
| フェーズ | Phase 5.5 実機検証・機能安定化 |
| ステータス | 未着手 |
| 目的 | 実機で見つけた問題を混ぜずに1件ずつ解決し、再発を自動テストで防ぐ |

## 着手順

1. セキュリティCritical / High
2. Blocker
3. High
4. 依存先となる共通原因
5. Medium
6. Low

優先度が同じ場合は、データ破損リスク、再現率、主要導線への影響、回避策の有無で決める。実装中のIssueは常に1件だけにし、探索で新しいIssueを起票しても現在の修正へ混ぜない。

## 1 Issueの完了サイクル

1. **トリアージ**: 重複、仕様どおり、バグ、仕様変更候補を分類する
2. **仕様確認**: `spec/features/`、`spec/screen-designs/`、API、データモデルを確認する
3. **再現**: Issueの最小手順で再現し、失敗するテストまたは観測値を得る
4. **根本原因**: 問題 → 直接原因 → 構造的原因で整理する
5. **修正範囲**: 1関心事に限定し、別の改善はFollow-up Issueへ分ける
6. **テスト**: 回帰テスト、正常系、境界値、関係するAPI認可を追加する
7. **実装**: 仕様と画面設計どおりに修正する
8. **自動検証**: `pnpm lint && pnpm typecheck && pnpm test && pnpm build`
9. **監査**: `security-audit`でCritical / Highゼロを確認する
10. **dev検証**: 修正版をdevへデプロイし、Issueと同じ実機・条件で再確認する
11. **回帰**: 直接の導線だけでなく、共有コードを使うlog / cellar / noteを確認する
12. **完了記録**: Before / After、テスト、残リスク、証跡、対象コミットをIssueへ記録する

## PRの単位

- 原則1 Issue = 1 PR
- spec変更が必要なら同じPRで先に正本を更新し、画面変更は受け入れチェックを貼る
- 共通関数の変更では全呼び出し元を列挙し、対象外機能の回帰テストを含める
- DB変更は`db-migration`スキルに従い、devデータのforward migrationを用意する
- 新依存・AIモデル・外部送信先はライセンス、サイズ、CSP、プライバシー、代替案をPRに記載する
- Issue外のリファクタリングや見た目変更を混ぜない

## 再オープン条件

- 同じ手順で再現する
- 回避策を使わないと主要導線が完走しない
- 別端末で同じ根本原因が確認できる
- 修正によりlog / cellar / noteの別用途が壊れた
- 計測値だけ改善し、正しさ・画像品質・データ整合性が悪化した

## 受け入れ条件

- [ ] 同時に実装中のIssueが1件
- [ ] 修正前の再現証跡または失敗テストがある
- [ ] 根本原因と変更範囲がIssueに記録されている
- [ ] 回帰テストが先に失敗し、修正後に成功することを確認している
- [ ] lint / typecheck / test / buildとセキュリティ監査が成功
- [ ] 同じ実機・条件で再現しない
- [ ] 共有コードの影響先を再確認している
- [ ] 未解決事項を別Issueへ分け、現在のIssueを曖昧なまま閉じていない
