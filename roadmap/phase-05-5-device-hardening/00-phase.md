## 目的

Phase 3〜5の飲酒記録・セラー・テイスティングノートを、オーナーの実機とdev環境で探索的に操作する。仕様や自動テストでは見つけにくい端末依存、待ち時間、失敗復帰、データ不整合を再現可能なIssueにし、同時着手1件で解決する。

Phase 6の実機QAとは責務を分ける。

| Phase | 主に確認すること |
|---|---|
| Phase 5.5 | Phase 3〜5の機能、データ、写真処理、API待ち時間、失敗・再試行、機能間連携 |
| Phase 6 | PWAインストール、standalone、Service Worker、セーフエリア、表示、a11y、Lighthouse、E2E |

## 依存

- Phase 5の5-01〜5-05が完了し、MVPの3機能がdev環境へデプロイできる
- [spec/dev-deploy.md](../../spec/dev-deploy.md) のdev環境を使える
- 実データを公開せずに再現できるテストアカウントとテスト用写真がある
- Issue起票には [実機QAテンプレート](../../.github/ISSUE_TEMPLATE/device-qa.yml) を使える

## ゴール（フェーズDoD）

- 主要導線と失敗・復帰ケースを、少なくともオーナーの主利用実機1台で実施し、端末・OS・ブラウザ・結果を記録している
- 発見事項を「Issue化」「重複」「仕様どおり」のいずれかへ分類し、未トリアージを残さない
- [Issue #48](https://github.com/akihotsuji/alco-app/issues/48) のP0/P1を分割・解決・実機再確認し、P2/P3は計測結果に基づいて実施・延期・不採用を決める
- Blocker / Highの未解決機能不良がゼロ。残すMedium / Lowには理由、回避策、後続Phase、オーナー判断がある
- 各修正に回帰テストがあり、lint / typecheck / test / buildとセキュリティ監査を通している

## 優先度

| 優先度 | 判定 | 扱い |
|---|---|---|
| Blocker | 保存不能、データ消失・破損、認証・認可の重大不良、主要導線が完走不能 | 他の修正を止めて最優先。Phase終了不可 |
| High | 回避困難な主要機能不良、頻発するクラッシュ・タイムアウト、誤保存 | Phase終了までに解決 |
| Medium | 回避策がある機能不良、顕著な遅さ、限定端末の問題 | 原則解決。延期は根拠と後続Phaseを記録 |
| Low | 文言、軽微な表示、頻度の低い違和感 | Issue化し、終了判定で扱いを決める |

セキュリティ規約のCritical / Highはこの表より優先し、発見時点で作業を止めて修正する。

## Issue運用

1. 1つの観測可能な問題だけを1 Issueにする
2. 端末、OS、ブラウザ、接続条件、前提データ、最小再現手順、期待結果、実結果、再現率、証跡を記録する
3. 推測と事実を分ける。原因が未確定ならタイトルや本文で断定しない
4. 重複は既存Issueへ証跡を追加し、新しい修正PRを増やさない
5. 実装前に該当spec・画面設計と照合し、「バグ」か「仕様変更」かを決める
6. 仕様変更なら先にspecと画面設計を更新し、オーナー承認後に実装する
7. 実データ、メールアドレス、ラベルの個人情報、Cookie、トークンをIssue・ログ・画像に載せない

## 変更の単位

- 同時に実装するIssueは1件
- 1 Issue = 1関心事 = 1PRを原則とする
- 共通の根本原因で不可分な場合だけ、Issueへ理由と影響範囲を書いて同じPRにする
- 修正PRには再現テスト、正常系、関係する認可テスト、実機再確認手順を含める
- リファクタリング、ランタイム変更、モデル交換を確定バグ修正へ同梱しない

- 根拠のないAIモデル交換、画像品質低下、COOP / COEP追加
