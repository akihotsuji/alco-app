# 1-01 画面一覧とナビゲーション構造

| 項目 | 内容 |
|---|---|
| フェーズ | Phase 1 設計 |
| ステータス | **レビュー待ち**（成果物: [spec/screens.md](../../spec/screens.md)） |
| 要件 | モバイルファースト、下部タブ想定（[spec/03-roadmap.md](../../spec/03-roadmap.md)、[spec/00-overview.md](../../spec/00-overview.md)） |
| ソース | Phase 1 デザイン「画面一覧とナビゲーション構造の決定」 |

## 1. 概要

アプリに存在する画面と、下部タブを中心とした遷移を確定する。実装（React Router）は Phase 2-05。本タスクは情報アーキテクチャの文書化。

## 2. 前提条件

- [spec/01-requirements.md](../../spec/01-requirements.md) の MVP 範囲
- 実装コードは不要
- オーナーがタブ構成を承認すること

## 3. スコープ

**対象**

- 認証前画面（ログイン、サインアップ）
- 認証後の下部タブ 5 つ案: ホーム / 記録 / セラー / ノート / 設定
- 各タブ配下のサブ画面（一覧・詳細・作成・編集）
- 404、未ログイン時リダイレクト

**対象外**

- ビジュアル（1-02、1-03）
- v1.x の目標設定画面の詳細（存在だけ「将来」と書く）
- 実装

## 4. 成果物

- [spec/screens.md](../../spec/screens.md)（ファイル名は推奨どおり確定）
- 画面 ID 一覧（後の API・テストで参照できる短い slug）

## 5. 細分化タスク

1. 要件から画面候補を洗い出す
2. タブ数とラベルをオーナーに確認する（5 タブは狭い）
3. 各画面の入場経路（タブ、ディープリンク、戻り）を表にする
4. 認証境界（ガードするルート）を書く
5. オーナー承認を得る

## 6. 手順

1. `spec/screens.md` を新規作成する（実装なし）。
2. 下記「仕様詳細」の草案を貼り、差分をオーナーレビュー用に明示する。
3. 承認後、Phase 2-05 がこのファイルを正本にする旨を 1 行書く。
4. PR: `docs: 画面一覧とナビ構造を追加`。

## 7. 仕様詳細

### 認証前

| ID | 画面 | 備考 |
|---|---|---|
| auth-login | ログイン | メール + パスワード |
| auth-signup | サインアップ | メール + パスワード。招待制は採用しない |
| auth-age | 年齢確認 | Phase 8。MVP では出さない |

未ログインで認証後 URL に来たら `auth-login` へ。

### 認証後タブ（ロードマップ案）

| タブ | ラベル案 | ルート案 | 主画面 |

| cellar | セラー | `/cellar` | ボトル一覧 |

| settings | 設定 | `/settings` | ログアウト、アカウント |

**確定（2026-09-04）**

- 5 タブを維持。ホームと記録は分ける。記録タブ中央案は不採用（詳細は [spec/screens.md](../../spec/screens.md)）
- タブアイコン（絵文字禁止で SVG にする等）は 1-03

### 設定に含める MVP

- ログアウト
- 表示名（任意項目。独立画面は作らない）
- 招待コード入力は置かない（招待制は採用しない）

## 9. セキュリティ観点

- クライアントのルートガードは UX。認可は API（security.mdc）
- 他ユーザーのリソース ID を URL に含む設計（`/cellar/:id`）は IDOR テストの対象。推測困難な ID を Phase 1-04 で選ぶ
